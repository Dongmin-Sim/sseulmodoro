# 파이프라인의 시작: 데이터 전체 재적재(Full Load)와 베이스라인 수립

## 들어가며
<!-- 이 글에서 무엇을 소개하려는지 -->

이번 글에서는 프로젝트에서 
비즈니스 의사 결정 시 지표로 사용되는 서비스 db 데이터를 데이터 웨어하우스로 사용하고 있는 BigQuery에 적재하는 파이프라인 구축한 과정을 소개드리고자 합니다

## 배경
<!-- 기존 구조와 그 선택이 유효했던 조건 -->

### 기존 구조
<!-- 소스, 데이터 형태, 아키텍처 -->

- 현재 아무것도 없음. 

## 요구사항

- 웹 서비스 소스 DB(Postgres)에서 지표 산출을 위한 데이터를 수집 필요

## 해결 방안 모색
<!-- 고려한 선택지와 각각의 트레이드오프, 대안 검토 -->

- 데이터 Latency/Freshness 요구사항이 낮다고 가정. 배치 방식으로 결정
- 소스데이터의 변경분 식별이 가능하지만(증분키 후보 존재), 서비스 초기 데이터의 양이 적다는 것을 가정

## 문제 개선
<!-- 무엇을, 왜. 특히 "선택하지 않은 이유" -->

### 결정 내용

- 위 사항 및 복잡도를 고려하여 Full Refresh 방식 결정 (전체 추출 + overwrite 적재)

### 새로운 아키텍처

- 추출 방법
  - psycopg로 소스 데이터베이스 테이블 전체 조회
  - pandas.DataFrame 변환하여 메모리 임시 적재
- 적재 방법
  - BigQuery WRITE_TRUNCATE Job 옵션으로 overwrite 벌크 적재

## 구현 시 고민한 점
<!-- 실제로 어려웠던 것, 고민한 것 -->

- 적재 전 컬럼 타입 일치를 위한 전처리 수행 (벌크 적재 시 bq 내부 df -> parquet 변환 동작 때문)
- 동작 방식: 단일 load job의 커밋 시점에 truncate+append가 원자적으로 반영
- 실패 시 기존 데이터 유지(원자성) + 재실행 시 동일 결과(멱등성)로 재실행 안전

## 남은 문제
<!-- 다음 글로 이어지는 고리 -->

- 데이터가 커질수록 데이터 추출을 위한 데이터 스캔 비용이 선형적으로 증가함. 이에 따른 여러 문제가 발생 가능함.
- 전체 재적재 시간 증가, Job 수행 인스턴스 메모리 가용량에 따라 OOM 발생 가능 
- 소스 DB 풀스캔으로 운영 시 부하 가능. 증분 추출로 스캔 범위 축소 고려
