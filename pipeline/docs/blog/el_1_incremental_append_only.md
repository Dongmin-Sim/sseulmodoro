지금 문제 전체 재적재를 진행하는 테이블은 원본 소스에 다음 두 테이블 
- pomodoro_sessions
- activity_log 

소스의 두 테이블은 성격이 다르다. 
- pomodoro_sessions 은 포모도로의 묶음(25 * 4) 으로 유저당 하루 평균적으로 2~3정도 생성된다고 가정. 
- 반면 activity_log는 서비스앱에서 발생되는 서비스 이벤트를 한곳으로 모은 테이블. append_only

우선적으로  activity_log의 경우에는 발생하면 수정되지 않는 append_only 성격의 테이블임. 

## 요구사항

> 매 주간 full-refresh 방식으로 적재되던 데이터가 일간 요청으로 변경되면서 파이프라인이 실패가 발생했다고 가정해봄.  
> 어떻게 처리할 건지?  

현재 full-refresh 방식의 데이터 업데이트 로직을 증분으로 변경하려면 어떤 점들을 고려해야할까?  

## 해결 방안 모색
<!-- 고려한 선택지와 각각의 트레이드오프, 대안 검토 -->

1. 일단 제일 먼저 떠오르는 간단한 방법은 "파이프라인의 처리 spec을 올린다." 
인데 full-refresh 방식은 결국 전체 데이터를 가져오는 방식이므로 소스 데이터의 양이 늘수록, 
결국에는 늘린 처리 spec에 도달하는 것도 시간 문제라고 생각했다.
2. 청크(메모리 개선)/병렬(시간 개선)로 나눠읽는다. => 그래도 DB 는 전체 스캔함. / 
3. 증분 데이터를 변경분만 읽는다. => DB 부분 스캔, 처리 양 적음.

### 증분 처리방식이란?

이를 증분처리방식을 통해 해결할 수 있다. 
Full refresh 방식은 원천시스템의 전체 데이터를 가져와 적재한다면. 
증분 처리 방식은, 원천 데이터에서 새로 추가되거나 변경된 데이터만 추출하여 적재하는 방식을 말한다.

증분 처리 방식의 경우 신규 혹은 변경분만 처리하면 되어 리소스 사용이 줄지만, 그에 비해 신경써야하는 부분이 전체 갱신 방식보다 훨씬 많이 늘어나게 된다. 

- 일단 `새로 추가`되거나 `변경된` 데이터를 탐지할 수 있어야한다.
- 그렇게 찾은 값을 타겟 데이터 시스템에 어떻게 `쓰냐/적재`하냐 에 대한 고민도 필요해진다.
- 그리고 어디까지 진행했는지 `상태`가 필요해진다.

그리고 증분처리방식으로 전환을 고려할때는 다음과 같은점.
- 처리 시간이 너무 오래걸릴때, 
- 비용의 증가가 문제가 될때, 
- 신규/변경 분이 전체 데이터의 아주 작은 일부일때 -> 효율성.
- 소스데이터가 변경되지 않는 성격일때(append-only)

### 소스 테이블 파악. 

소스 테이블의 성격은?

이때 탐지할때는 소스 테이블의 성격이 중요해진다. 
- 해당 테이블에 데이터가 생성만되는지 (Only Insert)
- 데이터가 갱신이 되는지? 
- 데이터가 삭제도 되는지?


일단 full refresh 방식으로 가져오는 소스 테이블의 성격부터 확인해봤다.

증분 갱신의 구분 
증분을 하려면 일단 현재까지 적재된 데이터와 아직 적재되지 않은, 변경이 있는 원 소스 데이터간의 비교할 수 있는 기준점이 필요함. 

이때 원 소스에 비교할 수 있는 기준이 될 수 있는 컬럼이있는지 확인이 필요함. 이를 증분 키라고 함. 주로 날짜를 이용하여 비교하여 가능함.(created_at, updated_at)

### 구현 방식 1 

- 증분 키는 Id 로
  - 구간 삭제 후 append / staging + merge
- 파이프라인이 돌지 않아도, 배치 한번만 처리하면됨. / 지연 도착문제에 비교적 강함. / 시간 타임존 고려 안해도 됨. 

### 구현 방식 2 

- 증분 키를 날짜로, created_at 추출
- 이 방식으로 했을 경우, 장점. 
- raw에 날짜 파티셔닝, 날짜를 기준으로 파티션 교체하는 방식. 
  - id 로 잡을 겨웅 이게 어려움. 왜냐하면 Bq 테이블의 파티셔닝을 할때, id 는 미리 범위를 잡기 애매함. 
    - → 추출을 버킷 경계에 맞추면 되긴 해. 진짜 문제는 그 버킷이 언제 확정되는지 알 수 없고, 끝값을 미리 정해야 하고, 사람이 쓰는 단위(날짜)와 무관하다는 것.
  - delete 안해도 됨. 
- 또 장점. 추출 로직과 백필 로직을 하나로


처리 범위가 "열린 구간"에서 "닫힌 구간"이 된다.
  id      WHERE id > since           시작만 있음. 끝은 항상 "지금까지 전부"             
  날짜     WHERE created_at = 3/15    시작과 끝이 둘 다 있음
- 증분 추출 코드와 백필 코드가 일원화 됨. (축이 하나라., 보통 백필은 날짜 단위로 하지 id 단위로 하지 않음. ) => 관리가 편해짐. 
- 백필이 쉬워짐, 적재가 DELETE 없이 파티션 교체 한 번으로 끝나서

### 재실행 시 안전? 멱등?

이렇게 증분 처리 방식으로 구현된 데이터 파이프라인은 멱등성을 보장해야한다.
- 기존 전체 재적재 방식은 별도의 멱등성을 고려할 포인트들이 적었음. 왜냐. 전체 처리는 매번 처음부터 다시 만들기 때문에 자연히 멱등성(idempotency)이 보장되고 결과가 항상 일관되는 반면
- 증분처리 방식은 변경분이나 새로운 값을 타겟에 저장할때 중복 저장되지 않도록 추가적인 설계가 필요해짐. merge, upsert

추출과 적재시에는 같은 컬럼을 기준으로 해야 데이터 유실이 없음.

### 추출 개선 

적재를 새로할때도 매번 소스에서 추출함. -> 소스 부하 부담. 
- GCS 추출시 파일 형태로 추출, 저장.
  - 이렇게 되면 장점. 
  - 매번 적재시마다 소스에서 추출안해됨. 소스에서 추출 딱 1번만. 부담 저하. 
  - 추출과 적재를 분리, 실패 전파를 추출까지 안가도 됨.
